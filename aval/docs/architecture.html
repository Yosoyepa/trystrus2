NextWave 2026 · The buyer who isn't human

Architecture and data flows

The whiteboard, drawn properly. One system picture, one happy path, and the order the checks run in. Definitions are at the bottom.

The problem

Nobody trusts a transaction made by an agent

A person tells an agent to buy something and the agent buys it. The merchant cannot check that the person agreed, and the person cannot prove afterwards what they agreed to. So merchants either block agents and lose real sales, or let them through as people and absorb the fraud.

The missing piece is a permission that can be written down, checked by a stranger, and taken away.

The system

The claim this drawing makes: the agent can look and propose, but only the rules engine can spend. There is no arrow from the agent to the merchant's payment API, and that absence is the design.

Figure 2

A purchase, start to finish

Marta authorizes flights to Córdoba under $150 until the end of the month. A seat appears at $130 and the agent buys it.

  1. Marta writes what she wants in Slack: flights to Córdoba, under $150, until 31 August, on her saved card.
  2. The BFF turns it into a mandate and asks her to approve it. She sees the exact terms before she signs.
  3. She signs. The signed mandate M-1 goes to the rules engine and the store. The agent never sees the card.
  4. The agent searches VuelaYa through its MCP server and watches prices.
  5. A seat appears at $130.
  6. The agent proposes the purchase. It does not buy. The proposal names the mandate it thinks covers it.
  7. The rules engine runs the three checks in figure 3.
  8. It pays through the merchant's API and includes the proof of M-1.
  9. VuelaYa verifies the proof itself and accepts, keeping its own verification record.
  10. Marta gets the receipt, and it says which mandate the purchase was made under.
  11. The decision goes into the log, chained to the one before it, and appears in the control tower.
Figure 3

The three checks, and what each refusal looks like

Order matters. An unknown agent is refused before we look at the mandate, and a dead mandate is refused before we look at the amount. Each refusal names the check that produced it.

Definitions

Every word on the board, in one line

The problem
Merchant
A company that takes payments. Ours is VuelaYa, a travel agency.
Purchasing agent
Software that finds, decides and buys on behalf of a person or a company.
Mandate
The permission a person gives their agent: what it may buy, up to how much, until when, with which payment method.
Verification
How the merchant checks that the agent buying from it is acting inside a real, live mandate from a real person.
Revocation
The person takes the permission back. Every purchase attempted after that has to fail.
Chargeback
The cardholder tells their bank they never authorized a payment, and the bank takes the money back from the merchant.
Human in the loop
A point where the agent stops and waits for a person to say yes. A stop, not a notification.
What the platform has to get right
Traceability
Every action leaves a record that ties the purchase to the person, the mandate and the rule that allowed it.
Idempotency
The same request sent twice buys once. Retries return the original result instead of a second flight.
Usability
Authorizing takes seconds from Slack or Telegram. If it feels like configuring a firewall, nobody does it.
Security
The agent never holds the raw card. It holds permission to use one the platform keeps.
Non-repudiation
Neither side can later deny what they did. Marta cannot say she never asked, and the merchant cannot claim an approval it never got.
Domain knowledge
A limit of the agent. It does not know what is normal for this buyer, so the rules and the history have to supply that.
Transaction access
A limit of the agent. It needs to see past purchases to know whether this one is a repeat and what it means.
The pieces
Auth
The boundary. Nothing enters the platform without a person attached to it.
BFF
One entry point for Slack, web and Telegram. It flattens all three into the same internal shape.
Agent
Searches, compares and proposes. It has no authority to move money.
Rules engine
Decides allow, ask, or refuse, and records the reason. No model runs inside it, so the same input always gives the same answer.
Mandates + transactions
Where signed mandates and purchase history live. The rules read from here.
Queue
Carries events between components so a slow merchant or a retry blocks nothing else.
Append-only log
Every decision, in order, each entry chained to the one before so a changed record is visible.
MCP server
The merchant's read side. How the agent explores what is for sale. Costs nothing, commits nothing.
Payment API
The merchant's write side. Only the rules engine calls it.
Control tower
One view of everything the agents have done, with who authorized it, which rule allowed it, and what the merchant returned.
